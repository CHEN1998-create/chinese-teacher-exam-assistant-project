# 教招有据：页面体验优化核心方案（双入口混合式）

- 文档版本：v1.0
- 更新日期：2026-10-08
- 文档状态：讨论结论汇总，待进入设计与开发
- 产品阶段：少量受邀用户验证，不以正式生产规模为目标
- 适用范围：公开首页、首次问答、初步结果、机会列表与详情、日程、备考、我的，以及全局导航和通用页面状态
- 本文目的：统一“为什么改、改成什么、先改什么、如何验证”的产品口径，并作为后续设计、开发、评审和面试复盘的共同参考

---

## 0. 一页结论

本次优化不以“换一套颜色”或“把按钮做得更漂亮”为目标，而是把当前信息完整但偏重、偏像说明文档和演示系统的页面，改造成一条更愿意让用户继续完成的产品旅程。

最终采用的核心方向是：

1. 首次体验采用**方案 F：双入口混合式**；
2. 页面遵守**一页一个任务、一屏一个主要行动**；
3. 使用**墨蓝 + 暖灰**主视觉，并遵守 **80 / 15 / 5** 用色比例；
4. 移动端使用**机会 / 日程 / 我的**底部导航，备考作为主要目标建立后的上下文入口；
5. 机会页大幅压缩，岗位卡片默认只显示五项信息；
6. 将“画像、匹配维度、规则版本、后端”等开发语言替换为用户语言；
7. 增加回答确认，但放在结果页顶部，不额外增加长流程；
8. 日程页从“日期展示”转为“下一项行动”；
9. 备考页根据用户阶段只展示当前状态，不同时堆叠全部模块；
10. 增加“继续上次进度”，完善加载、空状态、错误、成功与撤销反馈；
11. 未经人工审核的数据退出普通用户端；
12. 建立从首页开始填写到实际推进报名/备考的行为验证指标。

推荐体验主线：

```text
极简首页
├─ 直接开始匹配
└─ 先看 30 秒说明（可跳过）
        ↓
一组一页的问答
        ↓
每完成一组获得即时反馈
        ↓
信息足够时展示真实阶段性结果
        ↓
结果页确认已填写信息
        ↓
查看一个优先机会
        ↓
关注 → 日程行动 → 设置主要目标 → 备考
```

## 1. 目标澄清

### 1.1 原始诉求

产品功能逻辑已经较完整，但页面内容仍然偏多，首次用户需要阅读大量解释；界面存在卡片、状态色和操作入口较多的问题，整体更像一套说明完整的演示系统，而不是一个简洁、可信、愿意让用户继续填写的成熟产品。

本次希望汇总此前讨论结果，形成详细、可理解、可执行、可用于面试表达的核心方案。

### 1.2 显性目标

- 减少首次页面的阅读负担；
- 提升用户继续填写的意愿；
- 让解释信息仍然可找到，但不默认铺满页面；
- 统一按钮、颜色、卡片、导航和状态反馈；
- 压缩机会列表和岗位卡片；
- 建立明确的改造优先级和验收方式。

### 1.3 隐性期望

- 用户进入后能迅速理解产品价值；
- 用户每一步都知道为什么要继续；
- 页面呈现可信、克制、专业，而不是技术堆砌；
- 产品经理能够清楚解释每一项设计选择背后的用户问题和业务价值；
- 后续开发不会因为“想让页面更丰富”再次把所有内容堆回首屏。

### 1.4 一句话目标

> 用双入口、渐进提问、即时反馈和状态化页面，把“教招有据”改造成一个让用户快速进入、愿意填写、能够理解结果并继续推进报考行动的可信产品。

### 1.5 当前上下文

| 项目 | 当前情况 | 对本方案的影响 |
|---|---|---|
| 技术实现 | Next.js + React + Tailwind，已有组件和主要页面 | 本次无需更换技术框架 |
| 用户阶段 | 少量受邀用户验证 | 优先做好核心链路，不追求复杂视觉系统 |
| 主要用户任务 | 找机会、判断资格、关注、推进报名、进入备考 | 页面必须围绕行动，而不是围绕功能模块组织 |
| 当前首次流程 | 首页 → 五组问答 → 初步结果 | 可以渐进优化，不需要推倒重做 |
| 当前移动导航 | 已有机会 / 日程 / 我的底部导航 | 重点是统一职责和内容，不只是增加导航组件 |
| 当前桌面导航 | 固定侧栏，信息量偏大 | 需要评估收窄或改顶部导航 |
| 数据可信要求 | 机器提取必须人工审核后发布 | 未审核数据不能出现在普通用户推荐中 |
| 当前真实用户证据 | 可用性测试方案已存在，但尚缺完整实测基线 | 不能把设计判断包装成已验证结论 |

## 2. 当前页面的核心问题

### 2.1 信息不是无用，而是出现得太早

当前首页同时承担：

- 解释产品是什么；
- 展示监测范围；
- 证明信息来源；
- 说明匹配规则；
- 告知免责声明；
- 引导开始问答。

这些内容分别都合理，但在用户尚未体验价值前全部展示，会让首次页面像说明书。

### 2.2 页面视觉层级过于平均

多个圆角卡片、边框、浅色背景、状态标签和文字入口同时出现，导致重要内容和补充内容都获得了相似视觉权重。

### 2.3 问答过程“解释多于操作”

用户每一步不仅需要回答问题，还会同时看到覆盖范围、用途说明、跳过影响、保存说明、隐私说明和登录入口。用户的注意力被拆散。

### 2.4 结果页和机会页承担过多分类

机会页同时展示优先、其他符合、缺信息、人工确认、真实监测、地区不符、不符合和已截止等多类内容，逻辑完整但默认页面很长。

### 2.5 用户语言和内部语言混用

“画像、匹配维度、规则版本、AI 初核、后端正式结果”等词便于产品和开发沟通，但不是普通求职者自然使用的语言。

### 2.6 页面缺少完整的产品状态体验

成熟产品不仅要设计正常页面，也需要设计加载、无数据、网络失败、操作成功、误操作撤销、恢复上次进度等状态。

## 3. 设计总原则

### 原则 1：一页一个任务

每个页面只回答一个核心问题。若一段内容不服务于该问题，应下沉、折叠或删除。

### 原则 2：一屏一个主要行动

同一屏只能有一个高强调主按钮。其他动作使用文字入口、低强调按钮或按需展开。

### 原则 3：结论先于证据

先告诉用户“可能符合、还不能判断、下一步做什么”，再允许用户逐层查看原因、官方原文和版本记录。

### 原则 4：解释按需出现

不删除必要解释，而是分为：

1. 现在必须知道；
2. 部分用户需要时查看；
3. 做决定时再查看。

### 原则 5：反馈必须产生价值

不使用虚假积分或无意义庆祝。每次反馈应说明系统记住了什么、结果如何变化或下一步是什么。

### 原则 6：只展示可信数据

AI 提取候选和待审核记录属于内部工作状态，不能与已审核机会一起展示给普通用户。

### 原则 7：不因桌面更宽就展示更多内容

桌面端增加留白和阅读舒适度，不把移动端折叠的内容全部铺开。

## 4. 方案 F：双入口混合式首次体验

### 4.1 为什么选择方案 F

方案 F 同时照顾两类用户：

- **目标明确型用户**：已经知道自己想查什么，希望马上开始；
- **谨慎理解型用户**：担心资格判断不可靠，希望先了解系统怎么判断。

如果强制所有人阅读长文章，会增加进入门槛；如果完全没有解释，谨慎用户又可能不信任结果。双入口能够把选择权交给用户。

### 4.2 首页结构

```text
教招有据

看看你现在可能能报哪些教师岗位

根据官方公告逐项核对。
判断不了的条件，我们会明确标出来。

[ 开始匹配 ]

先花 30 秒了解我们怎么判断 →

杭州、宁波语文岗位持续核对中
```

首屏默认不再展示：

- 完整信息来源列表；
- 四档结果的详细定义；
- 多段免责声明；
- 下一招聘窗口长说明；
- 多张统计卡。

这些内容进入“当前覆盖范围”和“我们怎么判断”的次级页面或抽屉。

### 4.3 “先了解”路径

使用最多三张简短资讯卡，而不是长公众号文章：

#### 第 1 张：用户问题

> 看过招聘公告，为什么还是不知道自己能不能报？

公告中的学历、专业、身份和教师资格条件通常分散在正文与岗位表中。

#### 第 2 张：产品方法

> 我们会把公告要求和你的情况逐项核对。

每一条重要判断都可以回到官方公告查看依据。

#### 第 3 张：结果边界

> 判断不了的地方，会明确告诉你需要补充或向招聘单位确认。

预筛结果帮助你减少漏看，不替代招聘单位最终审核。

最后提供唯一行动：

```text
[ 开始匹配 ]
```

所有说明页均允许跳过。

### 4.4 问答过程

流程仍为五组，但页面只呈现当前任务：

1. 可接受地区；
2. 最高学历和学位；
3. 毕业证专业全称；
4. 毕业时间和就业状态；
5. 教师资格情况。

标准页面结构：

```text
← 返回                         第 2 / 5 组
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

你的最高学历是什么？

这会用于核对岗位的最低学历要求
为什么问这个？

○ 大专
○ 本科
○ 硕士研究生
○ 博士研究生

                    [ 继续核对学位 ]

                    暂时不确定
```

### 4.5 填写反馈

每完成一组，反馈分为四级：

| 反馈类型 | 示例 | 目的 |
|---|---|---|
| 操作反馈 | 选项出现勾选与选中状态 | 告诉用户操作已生效 |
| 理解反馈 | 已记住：杭州优先，宁波可以考虑 | 让用户确认系统没有理解错 |
| 价值反馈 | 之后不会推荐你明确不考虑地区的岗位 | 解释为什么值得继续填 |
| 阶段结果 | 当前有 8 个机会进入候选范围，仍需核对专业 | 提供真实的继续动力 |

阶段性数量必须由真实计算产生。数据不足时使用定性反馈，不得虚构数字。

### 4.6 继续上次进度

存在未完成草稿时，首页主行动改为：

```text
继续上次填写
还差教师资格信息

[ 继续填写 ]
```

已完成问答时不再回到营销首页，直接进入最新机会或上一次未完成行动。

## 5. 信息呈现的三层结构

| 层级 | 默认状态 | 内容 | 推荐组件 |
|---|---|---|---|
| 第一层 | 默认显示 | 当前结论、当前问题、下一步 | 页面主体 |
| 第二层 | 用户触发 | 为什么问、术语解释、填写示例、主要风险 | Popover、底部面板、右侧抽屉 |
| 第三层 | 决策时查看 | 官方原文、岗位表、版本、完整证据、纠错 | 详情页、证据抽屉 |

使用规则：

- 一句话能说清的提示放在问题下方；
- 只有部分人需要的信息使用“为什么问这个？”；
- 手机端长解释使用底部面板；
- 桌面端长解释使用右侧抽屉；
- 不使用仅靠鼠标悬停才能看到的 Tooltip；
- 大多数人必须知道的信息不能被隐藏。

## 6. 视觉系统

### 6.1 视觉定位

期望气质：

> 平静、可信、专业，像一位认真核对公告的招聘顾问。

不采用：

- 传统政务网站的大量红蓝色块；
- 考试培训网站的高饱和营销色；
- 过度卡通和游戏化；
- 企业后台式卡片阵列；
- 大量渐变、阴影和装饰图标。

### 6.2 推荐配色：墨蓝 + 暖灰

| 角色 | 色值 | 用途 |
|---|---|---|
| 页面背景 | `#F7F7F5` | 主画布，替代蓝色渐变 |
| 内容表面 | `#FFFFFF` | 必要的卡片、抽屉、弹窗 |
| 主文字 | `#1D292F` | 标题与主要正文 |
| 次级文字 | `#5F6B72` | 辅助说明与元信息 |
| 品牌主色 | `#2F566D` | 主按钮、选中、主要链接 |
| 品牌悬停 | `#244657` | 主按钮悬停/按下 |
| 品牌浅色 | `#EAF0F3` | 轻量选中和提示背景 |
| 默认边框 | `#E3E7E8` | 输入框、分隔线 |
| 成功 | `#3F6B55` | 已完成、已满足 |
| 提醒 | `#8A6428` | 待补充、时间提醒 |
| 风险 | `#A54646` | 明确失败或不可逆风险 |

### 6.3 80 / 15 / 5 用色比例

- **80% 中性色**：暖白、白色、深灰文字、浅灰边框；
- **15% 品牌色**：主按钮、选中状态、关键链接；
- **5% 状态色**：成功、提醒、风险。

状态色使用约束：

- 绿色不再铺满整张普通信息卡；
- 黄色只表示确实需要确认或临近行动；
- 红色只表示明确失败、不可逆风险或严重错误；
- 状态必须同时带文字或图标，不能只靠颜色表达。

### 6.4 字体与排版

- 使用现有系统中文字体栈，不增加境外字体依赖；
- 页面主标题建议 28–32px；
- 问题标题建议 22–24px；
- 正文 16px；
- 辅助文字最低 13–14px，重要说明不得长期使用 12px 浅灰字；
- 正文行高约 1.6；
- 长文字阅读宽度控制在 36–42 个中文字符；
- 页面只保留 3 个主要字号层级。

### 6.5 圆角、边框和阴影

- 页面容器不默认使用卡片；
- 可选择答案使用 10–12px 圆角；
- 普通输入框使用 8–10px 圆角；
- 默认卡片无阴影或仅使用极轻阴影；
- 不同时叠加明显边框、背景色和阴影；
- 虚线框只用于真正的上传/添加区域，不用于普通次要操作。

## 7. 按钮和操作层级

### 7.1 主操作

- 每个页面或独立操作区域只有一个主按钮；
- 手机端高度 48px、全宽；
- 桌面端高度 44–48px，宽度由内容或 280–320px 控制；
- 使用品牌墨蓝实心背景；
- 使用动作和结果明确的文案。

推荐：

- 开始匹配；
- 继续核对专业；
- 查看匹配结果；
- 查看判断依据；
- 继续准备材料。

避免：

- 确定；
- 提交；
- 下一步；
- 立即体验更多功能。

### 7.2 次要操作

以下操作使用文字入口或低强调按钮：

- 先了解我们怎么判断；
- 返回修改；
- 暂时不确定；
- 稍后处理；
- 查看全部结果。

### 7.3 危险操作

删除数据、放弃目标等不可逆操作，只有在确认弹窗中使用红色实心按钮。

### 7.4 选择控件与按钮的区别

- 答案选项是“可选择内容”，选中后显示边框、浅底和勾选；
- 主按钮是“执行下一步”，使用实心品牌色；
- 不能让所有选项看起来都像主按钮。

## 8. 每个页面的唯一任务

| 页面 | 唯一要回答的问题 | 首屏主行动 |
|---|---|---|
| 首页 | 这个产品能帮我什么，值不值得开始？ | 开始匹配 |
| 30 秒说明 | 它怎样判断，是否值得信任？ | 开始匹配 |
| 问答页 | 当前需要回答什么？ | 完成本组并继续 |
| 初步结果 | 我可能适合哪些机会？ | 查看一个优先机会 |
| 机会列表 | 现在最值得关注哪个？ | 查看优先机会 |
| 机会详情 | 为什么可能符合，下一步做什么？ | 关注 / 补信息 / 准备报名 |
| 日程 | 下一件不能错过的事是什么？ | 处理下一项行动 |
| 备考 | 我今天只需要完成什么？ | 开始今日任务 |
| 我的 | 我的资料、目标和设置在哪里？ | 进入当前最相关项目 |

页面评审规则：如果首屏存在两个同等重要的问题，则页面尚未完成收敛。

## 9. 全局导航

### 9.1 移动端

底部导航采用三项：

```text
机会    日程    我的
```

职责：

- **机会**：寻找、判断、关注岗位；
- **日程**：推进报名动作和官方节点；
- **我的**：主要目标、报考信息、备考入口、资料、通知、隐私与账号。

备考不作为首次就固定出现的一级 Tab；只有用户设定主要目标后，才从“我的主要目标”和相关上下文进入。

移动导航要求：

- 高度约 64px，并考虑手机安全区域；
- 图标 + 文字同时显示；
- 激活状态不只依赖颜色；
- 二级详情页保留原 Tab 高亮；
- 问答、登录和 30 秒说明不显示底部导航。

### 9.2 桌面端

优先评估顶部导航：

```text
教招有据             机会  日程  我的             头像
```

若继续使用侧边栏：

- 宽度从当前规格适当收窄；
- 删除常驻的大型目标卡；
- 只保留品牌、三个入口和账号；
- 主要目标放回相关内容页，不在所有页面重复展示。

### 9.3 为什么这样改

- 产品一级任务只有三个，宽侧栏会显得像复杂后台；
- “我的”能够承接设置、资料、隐私和备考入口，减少导航项；
- 备考需要主要目标作为前置，直接放在一级导航会让尚未选目标的用户进入大量空状态。

## 10. 回答确认：增加信心但不增加长流程

不新增强制的“第六步确认页”。完成问答后，在结果页顶部展示简短摘要：

```text
根据这些信息为你判断

杭州优先 · 宁波可以考虑
本科学士 · 汉语言文学（师范）
2026 年毕业 · 已取得高中语文教师资格

修改报考信息
```

用户点击某一项时，直接回到对应组，而不是重新从第一组开始。

这样做的好处：

- 用户确认系统没有理解错；
- 减少因填错一个字段导致结果不可信；
- 不增加新的强制页面；
- 结果与输入建立可理解的因果关系。

## 11. 机会页大幅压缩

### 11.1 默认结构

```text
最值得关注
1 个优先机会（完整卡片）

其他可能适合
2–3 个简化卡片

还不能判断
5 个机会需要补充信息

查看其他结果（12）
```

“其他结果”中再包含：

- 明确不符合；
- 已截止；
- 地区不在选择范围；
- 历史留档。

### 11.2 不再在用户端展示

- AI 初核待人工复核的真实监测记录；
- 内部提取状态；
- 规则调试信息；
- 面向工作人员的版本处理状态。

这些内容只进入管理后台。

### 11.3 为什么压缩

- 用户的目标不是阅读所有分类，而是找到值得推进的机会；
- 默认展示过多失败和过期内容，会削弱价值感；
- 列表页负责“做选择”，详情页负责“看证据”；
- 大幅缩短页面能让优先机会和下一步更明显。

## 12. 岗位卡片：默认只显示五项信息

### 12.1 五项信息

1. 地区 + 岗位名称；
2. 用工性质 + 学段 + 招聘人数；
3. 匹配状态；
4. 报名截止时间；
5. 一句最关键依据或风险。

加上一个唯一主行动：

```text
[ 查看判断依据 ]
```

示例：

```text
杭州 · 初中语文教师
事业编 · 招 3 人

可能符合                         还有 6 天截止

学历和教师资格符合，专业范围需要确认

[ 查看判断依据 ]
```

### 12.2 从列表卡片下沉到详情页

- 官方原文；
- 岗位表附件；
- 完整条件清单；
- 公告版本；
- 多个关注标签；
- 纠错入口；
- 规则版本；
- 详细来源定位。

### 12.3 内容预算

- 最多五项事实；
- 最多一个状态标签；
- 最多一句解释；
- 最多一个高强调按钮；
- 默认高度尽量稳定；
- 不在一张卡片同时展示三个以上徽章。

## 13. 开发语言替换为用户语言

| 内部/当前表达 | 用户表达 | 使用说明 |
|---|---|---|
| 基础画像 | 你的报考信息 | 用户不需要理解“画像”概念 |
| 即时匹配已发布公告 | 根据最新公告重新核对 | 描述用户能感知的行为 |
| 匹配维度 | 报考条件 | 使用招聘语境 |
| 闸门失败 | 这个机会暂时不能推荐 | 不暴露内部规则结构 |
| UNKNOWN | 还不能判断 | 中文、可行动 |
| MANUAL_REVIEW | 建议向招聘单位确认 | 说明下一步 |
| 数据集 | 信息来源 | 去技术化 |
| 规则版本 | 判断依据更新于 | 仅必要时展示 |
| 服务端正式结果 | 最新结果 | 用户不关心运行位置 |
| localStorage | 仅保存在这台设备 | 描述实际影响 |
| API/后端加载失败 | 内容暂时没有加载出来 | 说明用户处境 |
| AI 初核 | 待工作人员核对 | 普通用户端原则上不展示 |
| 主要目标 role=primary | 主要备考目标 | 技术值不外显 |

文案规则：

- 先说明用户能做什么，再说明系统做了什么；
- 错误提示包含“发生了什么 + 数据有没有丢 + 怎么恢复”；
- 不使用“智能、精准、保证”等不可验证词；
- 不把“初步符合”写成“可以报名”或“报名成功率高”。

## 14. 空状态、加载、错误、成功与撤销

### 14.1 加载状态

- 机会列表使用与真实卡片形状一致的骨架屏；
- 详情页使用标题和条件行骨架；
- 避免所有页面只显示一个全屏转圈；
- 加载较长时用用户语言说明正在核对什么。

### 14.2 空状态

错误示例：

```text
暂无数据
```

推荐示例：

```text
当前已审核范围内还没有与你条件相符的机会

新公告核对完成后会自动出现在这里。
你也可以调整愿意前往的地区。

[ 修改地区 ]
```

空状态必须包括：

- 为什么为空；
- 这是否代表真的没有机会；
- 用户接下来可以做什么；
- 一个主要行动。

### 14.3 错误状态

```text
机会暂时没有加载出来

你填写的信息已经保存，可以稍后重试。

[ 重新加载 ]
```

不显示：后端、数据库、Mock、服务模式、接口地址等开发信息。

### 14.4 成功与撤销

关注岗位后：

```text
已加入关注
报名时间已经加入日程

撤销
```

能够安全撤销的动作优先提供“撤销”，而不是每次弹出确认框。

### 14.5 删除与不可逆操作

只有删除数据、放弃主要目标等不可逆操作使用确认弹窗，并明确说明影响范围。

## 15. 日程页改为行动页

### 15.1 页面目标

不回答“有哪些日期”，而回答：

> 我下一件不能错过的事是什么？

### 15.2 首屏结构

```text
今天需要处理

宁波市教师招聘
报名还有 3 天截止

材料准备 3 / 5

[ 继续准备材料 ]
```

### 15.3 第二层时间线

```text
接下来

10 月 12 日    报名截止
10 月 18 日    准考证打印
10 月 26 日    笔试
待官方通知      成绩查询
```

### 15.4 规则

- 默认使用时间线，不展示月历；
- 时间未定显示“待官方通知”；
- 不生成推测日期；
- 必须处理、建议处理、普通信息使用不同视觉强度；
- 时间冲突只提醒，不替用户放弃；
- 已完成事项自动收起；
- 过期事项进入历史；
- 用户可以关闭单个机会提醒并撤销。

### 15.5 产品价值

用户真正需要的不是看日期，而是避免漏掉报名、缴费、准考证和考试节点。行动页能够直接承接关注后的价值。

## 16. 备考页按状态呈现

备考页不同时展示所有功能，而是遵守状态机：

```text
未设置主要目标
→ 去选择主要目标

考试信息未确认
→ 核对考试内容

计划待确认
→ 确认 7 天计划

计划执行中
→ 今天只做这一项

完成一周
→ 进行周复盘
```

### 各状态首屏唯一行动

| 状态 | 主要信息 | 唯一行动 |
|---|---|---|
| 无主要目标 | 先选一个真正准备报考的机会 | 去选择主要目标 |
| 信息未确认 | 尚不能生成可靠计划 | 核对考试内容 |
| 计划草稿 | 展示 7 天安排摘要 | 确认计划 |
| 执行中 | 今天最重要的一项任务 | 开始任务 |
| 今日完成 | 今日已完成和明日预告 | 查看明日安排 |
| 周期结束 | 完成情况和调整建议 | 开始周复盘 |

本周其他任务、备选目标、资料诊断和计划历史全部进入第二层或第三层。

## 17. 动效与微交互

### 保留

- 页面切换 150–250ms 淡入或轻微位移；
- 答案选中时边框、背景和勾选变化；
- 进度条自然更新；
- 完成五组问答后一次轻量完成反馈；
- 关注、保存、撤销等状态变化的即时反馈。

### 删除或避免

- 假装 AI 正在输入；
- 无必要的等待动画；
- 每一步撒花；
- 所有卡片悬浮；
- 多个模块依次飞入；
- 自动轮播；
- 动画期间禁止用户操作。

### 无障碍要求

- 尊重系统“减少动态效果”设置；
- 动态状态变化应可被辅助技术识别；
- 弹层打开和关闭后正确管理键盘焦点。

## 18. 五项最高优先级改造

### P0-1：压缩机会页和岗位卡片

**为什么改**：机会页是用户完成问答后第一次真正感受价值的页面，目前信息分类和单卡内容最容易膨胀。

**怎么改**：默认只展示一个优先机会、少量其他机会和一个“还不能判断”汇总；岗位卡片限制为五项信息。

**用户收益**：更快找到值得关注的岗位，不需要理解系统全部分类。

**产品收益**：提升查看详情、关注和报名推进转化。

**关键假设**：减少默认信息后，用户仍能正确决定是否进入详情。

**验证方式**：让 5 名目标用户在 10 秒内指出最值得关注的机会、截止风险和下一步。

### P0-2：未审核数据退出用户端

**为什么改**：可信度是产品成立的基础，待审核内容即使标记清楚，也会增加用户判断负担并造成误用风险。

**怎么改**：AI 候选、待复核记录和提取状态只在管理后台显示；用户端只读已发布版本。

**用户收益**：看到的每条机会都具有明确可信层级。

**产品收益**：降低高影响事实错误和品牌信任风险。

**关键假设**：已审核数据数量能够支撑首批用户体验。

**验证方式**：检查普通用户所有接口与页面，不能访问或显示未审核候选。

### P0-3：按用户阶段显示页面

**为什么改**：同一页面同时展示未开始、待确认、执行中和完成后的模块，会让用户无法判断当前重点。

**怎么改**：为首页、问答、日程和备考建立明确状态，每种状态只给一个下一步。

**用户收益**：进入页面就知道现在应该做什么。

**产品收益**：减少无意义浏览，提高任务完成率。

**关键假设**：系统能够可靠识别用户当前阶段。

**验证方式**：为每个状态编写场景测试，并让用户用一句话复述页面当前任务。

### P0-4：完善空、错、加载和撤销

**为什么改**：正常路径之外的体验，是成熟产品与演示原型的重要区别。

**怎么改**：建立统一的骨架加载、解释型空状态、可恢复错误、成功反馈和可撤销操作。

**用户收益**：网络失败、无机会或误操作时仍知道下一步，且不担心数据丢失。

**产品收益**：降低退出率和重复提交，减少测试用户求助。

**关键假设**：大部分非理想状态都可以给出安全恢复路径。

**验证方式**：断网、接口失败、空数据、重复点击和误取消关注场景逐项测试。

### P0-5：建立行为验证目标

**为什么改**：如果没有数据，只能判断页面“看起来更好”，无法知道用户是否更愿意完成。

**怎么改**：建立首页理解、开始填写、每步完成、结果曝光、查看依据、关注、日程行动和开始备考的漏斗。

**用户收益**：后续优化会针对真实困难，而不是继续凭感觉增加功能。

**产品收益**：能够说明改版是否有效，也为面试和复盘提供证据。

**关键假设**：少量受邀用户的行为和访谈能够暴露主要问题。

**验证方式**：先做 5–8 人可用性测试，再根据真实样本建立基线；小样本不急于做统计显著性 A/B 测试。

## 19. 分阶段优先级

### P0：先解决核心体验与可信问题

1. 双入口首页；
2. 问答页信息减负与即时反馈；

9. 行动型日程页；
10. 空、错、加载、成功、撤销；
11. 继续上次进度；
12. 核心行为指标。

1. 墨蓝暖灰配色与 80/15/5 规则；

3. 收敛圆角、边框和阴影；

7. 动效规范；
8. 响应式与触控区域；
9. 统一术语、状态与图标。

### P2：有真实数据后再增强

1. 根据真实机会数量决定是否增加筛选；
2. 根据用户行为决定是否增加搜索；

- 完整 AI 聊天机器人；
- 强制公众号长文章；
- 复杂首页仪表盘；
- 地图找岗位；
- 能力雷达；
- 排行榜和积分；
- 复杂月历；
- 同时生成多套备考计划；
- 为显得高级而加入大量动画。

未审核数据退出用户端应与机会页改造并行执行，但属于发布前硬门槛。

## 22. 风险预判

| 风险 | 影响 | 预防措施 |
|---|---|---|
| 为了少字而隐藏必要信息 | 用户误解结果 | 三层信息设计；多数人必须知道的内容保持可见 |
| 阶段性结果使用虚假数字 | 信任受损 | 仅使用实时真实计算；不足时给定性反馈 |
| 双入口增加选择困难 | 首屏犹豫 | 只有“开始匹配”为主按钮，“先了解”为文字入口 |
| 机会页压缩后信息不足 | 用户不敢点进详情 | 保留五项核心信息，并进行 10 秒识别测试 |
| 底部导航新增但职责不变 | 只是换外观 | 同时验收页面职责、备考门禁和桌面入口 |
| 视觉改造覆盖业务正确性 | 好看但误导 | 可信数据和状态逻辑优先于视觉统一 |
| 未审核数据仍通过接口泄露 | 高影响错误 | 服务端限制用户端只读已发布版本 |
| 动效增加等待感 | 降低效率 | 动效仅解释状态变化，禁用假输入等待 |
| 小样本被解释成统计结论 | 决策失真 | 小样本只描述问题和行为，不宣称显著提升 |
| 一次修改所有页面 | 难以回归 | 按 P0 → P1 → P2 小步交付、逐模块验收 |
| 新旧术语并存 | 用户困惑 | 建立统一词表并全仓检查用户可见文案 |
| 设计系统过度建设 | 拖慢验证 | 只建立当前页面真正使用的 Token 和组件 |

## 24. 从产品视角解释“为什么这样改”

### 24.1 不是单纯做减法，而是重排价值出现的顺序

原页面把可信证明、边界和详细规则放在用户体验价值之前。改版后，用户先理解自己能得到什么，再按需要查看证据。信息没有消失，而是出现在更合理的决策时点。

### 24.2 双入口是在效率和信任之间做平衡

直接开始满足高意图用户；30 秒说明满足谨慎用户。产品不替用户决定必须先学习还是先操作。

### 24.3 阶段反馈解决的是“为什么还要继续填”

问卷最大的流失原因之一不是问题数量本身，而是用户不知道继续填写能得到什么。即时反馈把每一步输入转化为可感知价值。

### 24.4 压缩机会页是在帮助决策，而不是隐藏数据

列表页的任务是帮助用户选择优先机会；完整证据属于详情页。把所有信息铺在列表中，反而增加比较成本。

### 24.5 未审核数据退出用户端体现了可信产品的边界

教师招聘资格属于高影响信息。机器可以提高整理效率，但不能把待审核结果直接交给用户承担风险。

### 24.6 状态化页面让产品围绕用户，而不是围绕功能

用户在不同阶段需要的内容不同。按状态呈现意味着产品先判断“用户现在在哪里”，再给一条合适路径，而不是把所有功能都展示出来。

### 24.7 完善异常状态是在建立安全感

用户是否愿意输入信息，不只取决于正常页面是否漂亮，还取决于出错时数据会不会丢、能不能恢复、误操作能不能撤销。

### 24.8 行为验证让设计从审美判断变成产品决策

高级、简洁只是视觉感受；是否更容易理解、填写和推进，必须通过行为与访谈验证。

## 25. 对用户和产品分别有什么好处

| 改动 | 对用户的好处 | 对产品的好处 |
|---|---|---|
| 双入口 | 可以直接开始，也可以先建立信任 | 同时覆盖高意图和谨慎用户 |
| 一页一个任务 | 不需要同时理解大量信息 | 降低首次流失与误操作 |
| 即时反馈 | 知道填写产生了什么作用 | 提升继续完成的动力 |
| 回答确认 | 能发现系统理解错误 | 降低错误输入导致的低质量结果 |
| 压缩机会页 | 更快找到值得关注的机会 | 提升详情和关注转化 |
| 五项岗位卡 | 比较成本更低 | 形成稳定可复用列表组件 |

## 26. 面试表达参考

### 26.1 30 秒版本

> 我在这个项目里发现，问题不是功能不够，而是信息出现得太早、页面承担的任务太多。我的方案不是简单删字，而是采用双入口：高意图用户直接开始，谨慎用户可以先看 30 秒说明；问答一组一页，并在每一步给有价值的反馈。完成后把机会页压缩成一个优先机会和少量分组，完整证据放进详情。这样既保留教师招聘产品需要的可信度，又降低首次使用成本。

### 26.2 90 秒版本

> 这个产品早期为了保证可信，把覆盖范围、官方来源、规则边界和免责声明都放到了首页和问答页。内容本身没有错，但用户在看到价值前要阅读太多，页面也因为大量卡片和状态色更像演示系统。
>
> 我先重新定义了每个页面的唯一任务，再采用双入口混合式：首页只保留核心价值和“开始匹配”，同时给需要建立信任的用户一个可跳过的 30 秒说明。问答保持五组，但解释改成按需展开，每完成一组都反馈系统记住了什么以及结果如何变化。
>
> 结果侧重点从“展示系统所有分类”改成“帮助用户做下一步决定”。机会页默认突出一个优先机会，岗位卡片限制为五项信息；未审核数据完全退出用户端。日程从日期列表改成下一项行动，备考按用户阶段显示不同页面。
>
> 最后我没有把审美作为唯一标准，而是定义了首页理解、问答完成、查看依据、关注、日程行动和开始备考的漏斗，并计划用 5–8 名目标用户做可用性测试。这样设计决策既有用户价值，也有可验证的业务结果。

### 26.3 使用 STAR 结构表达

#### Situation：背景

产品已经具备机会匹配、日程和备考功能，但信息密度高，首屏解释多，用户难以快速理解主线。

#### Task：任务

在不牺牲资格判断可信度的前提下，降低首次使用成本，并让用户更愿意完成信息填写和后续行动。

#### Action：行动

1. 梳理每个页面的唯一任务；
2. 设计双入口首次体验；
3. 将解释分成默认、按需和证据三层；
4. 限制岗位卡片信息预算；
5. 把日程和备考改为状态驱动；
6. 建立加载、空、错、撤销等完整状态；
7. 定义行为漏斗和可用性测试。

#### Result：结果

当前尚未完成真实用户实测，因此面试中不能虚构完成率提升。可以如实表达为：

> 已形成可执行的改造方案、任务优先级和验证方法；下一步通过 5–8 名目标用户建立基线，再根据实际流失点迭代。

如果后续取得真实数据，再补充具体完成率、耗时和转化变化。

### 26.4 面试官可能追问

#### 为什么不用完整聊天机器人？

因为核心问题是降低阅读负担和建立节奏，不需要引入大模型、流式对话和额外不确定性。采用顾问式语气和一问一页即可获得主要体验收益。

#### 为什么不把所有解释都删掉？

资格判断是高影响场景，解释和证据不能删除，只能根据用户决策时点渐进呈现。

#### 为什么备考不放在一级导航？

备考需要用户先选择主要目标。没有目标时固定展示备考入口，会产生大量无意义空状态，也会让产品主线分散。

#### 为什么未审核数据必须退出用户端？

因为用户可能据此决定是否报名。机器候选可以提高内部效率，但高影响事实必须人工审核后才能成为用户依据。

#### 怎么证明改版有效？

先用可用性测试验证理解和任务完成，再观察开始填写、完成画像、查看依据、关注、日程行动和备考启动的漏斗变化。小样本阶段描述行为，不夸大统计结论。

#### 如果开发资源很少，先做什么？

先做机会页和卡片压缩、隐藏未审核数据、替换技术语言、完善异常状态；这些改动价值高、依赖少，也最能改变用户的第一感受。
