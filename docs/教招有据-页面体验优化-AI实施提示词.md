# 教招有据：页面体验优化 AI 实施提示词

## 使用说明

将本文件从“实施提示词正文”开始完整复制给能够读取并修改本仓库的编码 AI。最好让它在仓库根目录运行。该提示词授权修改本项目内与页面体验优化直接相关的代码、测试和文档，但不授权推送远程仓库、发布上线、删除用户数据或扩大产品范围。

# 实施提示词正文

你是一名资深产品设计工程师、前端工程师和谨慎的代码维护者。请基于现有仓库完成“教招有据”页面体验优化。你的目标不是制作一套静态视觉稿，而是在保留现有业务规则、数据可信边界、登录模式和测试能力的前提下，完成可以运行、可以回归、可以验证的真实产品改造。

本任务范围较大。请先审计，再按阶段小步修改和验证；不要推倒重写，不要只改颜色，也不要把未实现内容写成已完成。

基线审计完成标准：每个核心页面、关键数据来源、测试入口和用户已有改动都已被明确识别，没有把仓库当成空白项目。

## 三、不可改变的产品边界

1. 当前是少量受邀用户验证产品，不引入微服务、Kubernetes、Redis、消息队列、搜索集群或新的大型框架；
2. 保留 Next.js + React + TypeScript + Tailwind 前端和现有 NestJS/Prisma/PostgreSQL 后端；
3. 只开放语文学科的当前验证能力，但类型和页面不把语文写成永久唯一范围；
4. AI 只能生成候选提取或辅助内容，不能直接发布高影响事实，不能替招聘单位作资格认定；
5. 普通用户只能读取已经人工审核并正式发布的公告版本；该规则必须由服务端或数据访问层保证，不能只靠隐藏前端组件；
6. 未填写信息不能被判定为“不符合”；
7. 预筛结论不能写成官方资格认定或报名保证；
8. 保留演示模式与受邀模式的数据隔离，受邀模式不得静默回退到 Mock；
9. 保留旧路由兼容、访客草稿恢复、登录后迁移、关注、主要目标、日程和备考数据；
10. 国内普通网络必须可访问：不增加 Google Fonts、境外 CDN、浏览器直连境外 API 或运行时外部依赖；
11. 不把服务端密钥、管理员能力或内部数据状态暴露到浏览器；
12. 不提交、不推送、不发布，除非用户另行明确授权。

## 四、最终体验方向

采用“方案 F：双入口混合式”：

```text
极简首页
├─ 直接开始匹配
└─ 先看 30 秒说明（可跳过）
        ↓
一组一页的问答
        ↓
每完成一组获得即时反馈
        ↓
信息足够时展示真实阶段性结果
        ↓
结果页确认已填写信息
        ↓
查看一个优先机会
        ↓
关注 → 日程行动 → 设置主要目标 → 备考
```

所有用户端页面遵守：

- 一页一个任务；
- 一屏一个高强调主行动；
- 结论优先，解释按需展开，完整证据进入详情；
- 默认页面帮助用户行动，不展示系统所有能力；
- 桌面端通过留白提升舒适度，不把折叠信息全部展开。

## 五、视觉系统要求

### 5.1 色彩

建立语义化设计 Token，并逐步替换本任务涉及用户端页面的散落颜色：

| 角色 | 色值 |
|---|---|
| 页面背景 | `#F7F7F5` |
| 内容表面 | `#FFFFFF` |
| 主文字 | `#1D292F` |
| 次级文字 | `#5F6B72` |
| 品牌主色 | `#2F566D` |
| 品牌悬停 | `#244657` |
| 品牌浅色 | `#EAF0F3` |
| 默认边框 | `#E3E7E8` |
| 成功 | `#3F6B55` |
| 提醒 | `#8A6428` |
| 风险 | `#A54646` |

页面整体遵守 80 / 15 / 5：约 80% 中性色、15% 品牌色、5% 状态色。该比例是视觉约束，不需要编写脆弱的像素占比测试；通过组件语义和页面评审保证。

状态色规则：

- 绿色只表达已完成或已满足；
- 琥珀色只表达待补充、待确认或时间提醒；
- 红色只表达明确失败、严重错误或不可逆风险；
- 状态同时包含文字或图标，不只依赖颜色；
- 普通信息使用中性色，不铺大面积绿色、黄色或红色背景。

### 5.2 字体、间距与容器

- 保留系统中文字体栈，不添加任何网络字体；
- 正文以 16px 为主要阅读字号；重要辅助信息不得长期使用低对比度 12px；
- 页面主标题、问题标题、正文和辅助文字形成最多四级清晰层级；
- 使用统一的 4/8px 间距尺度；
- 问答/内容页建议最大宽度 640–720px；列表页可在 880–960px 内根据内容调整；
- 去除用户端问答页的蓝色渐变背景；
- 页面外层不默认套白色阴影卡；
- 同一个容器不要同时依赖明显背景、边框和阴影；
- 圆角收敛为少量等级；虚线框只用于真正的添加/上传区域。

### 5.3 品牌图形

- 用户端正式品牌位置不再使用 📝 等 Emoji 作为 Logo；
- 优先使用文字标识或简单、本地、自包含的 SVG/CSS 标记；
- 不新增远程图片或图标依赖；
- 普通功能图标保持同一套线性风格。

## 六、按钮和操作规则

重构或统一现有 `Button`、内部链接按钮和选择控件，使页面遵守：

1. 每个页面或独立区域只有一个高强调主按钮；
2. 主按钮使用品牌墨蓝色，手机端高度约 48px，桌面端 44–48px；
3. 次要操作使用 ghost/text/link，不使用第二个同等面积的实心按钮；
4. “暂时不确定”“返回修改”“先了解”“查看全部”使用低强调文字入口；
5. 危险实心按钮只在不可逆操作的确认界面出现；
6. 按钮文案说明结果，例如“继续核对专业”“查看匹配结果”“继续准备材料”，少用笼统的“下一步”“确定”“提交”；
7. 内部页面跳转使用正确的 Next.js Link，页面内动作使用 button；
8. 答案选项和执行按钮必须有不同视觉语义；
9. 避免没有解释的禁用按钮。无法继续时，在用户操作后将焦点移到缺失项并显示具体错误；
10. 关键触控目标建议达到 44×44px，并有清晰键盘焦点。

## 七、逐页面实施要求

### 7.1 公开首页 `/`

保留现有登录状态、访客草稿和完成状态的自动恢复逻辑，但重构首次访客界面：

- 首屏只保留品牌、核心价值、一句可信说明、当前覆盖的一行摘要、一个主按钮和一个“先了解”文字入口；
- 主按钮文案为“开始匹配”或同等清晰表达；
- 删除首屏完整来源列表、四档规则长说明和多张事实卡；
- 完整覆盖范围进入按需展开内容；
- 有未完成草稿时优先显示“继续上次填写”和剩余步骤；
- 已完成问答的访客继续进入结果；登录用户继续进入机会；
- 不宣称未经实测的完成时长。

首页完成标准：320px、375px、768px、1440px 下首屏主行动无需阅读长段落即可发现；返回用户不会重新开始。

### 7.2 “先了解我们怎么判断”

实现可访问、可返回、可跳过的简短说明体验。可以使用独立路由或现有页面内的可访问视图，但必须满足：

- 最多三个简短内容单元；
- 顺序为“用户为什么难判断 → 产品怎么核对 → 结果边界”；
- 全程可直接开始匹配；
- 不使用自动播放轮播；
- 浏览器返回键可预测；
- 手机和桌面均可使用；
- 该路径需要独立分析事件，但不采集个人信息。

### 7.3 首次问答 `/onboarding`

保留五组业务字段、草稿恢复、跳过语义、受邀模式同步和现有匹配规则，重构展示：

- 一组一页；
- 页面只显示返回、当前进度、当前问题、必要的一句提示、答案和一个主行动；
- 当前监测范围不在每一步重复展示；
- `STEP_PURPOSE` 等用途说明缩短，长解释放入“为什么问这个？”；
- “暂不提供”从全宽虚线按钮降为文字操作；
- 用户选择跳过后再说明该项对结果的影响；
- 专业输入提供可展开示例；
- 单选题只有在不会跳过关联字段、用户可轻松返回时才允许自动前进；其他情况保留明确继续按钮；
- 每完成一组显示不阻塞流程的即时反馈；
- 有真实计算支持时才展示阶段性机会数量；否则只显示定性反馈；
- 返回和刷新后答案、步骤、跳过状态保持正确；
- 保存失败时输入仍留在当前页面，并提供可执行的恢复方式；
- 不让虚拟键盘遮挡当前字段、错误信息或主操作。

### 7.4 初步结果 `/preview`

- 顶部增加“根据这些信息为你判断”的回答摘要；
- 摘要使用用户语言，包含地区、学历学位、专业、毕业/就业和教师资格；
- “修改”可直接回到对应问答组，不能强迫用户从第一组重新开始；
- 摘要不是额外的强制确认页；
- 首屏先展示一个优先结果和一个下一步；
- 其他分类渐进展开；
- 缺失信息明确为“还不能判断”，不能变成“不符合”；
- 登录要求只在关注、保存或需要跨设备恢复时出现；
- 登录后访客数据迁移保持幂等。

### 7.5 机会列表 `/opportunities`

把当前长列表压缩为：

1. 一个优先机会完整卡片；
2. 其他可能适合中的最多 2–3 个简化卡片；
3. “还不能判断”的数量和主要缺失原因；
4. “查看其他结果（N）”折叠入口。

“其他结果”再包含不符合、已截止、地区范围外和历史留档。覆盖范围以紧凑摘要呈现，完整说明按需展开。

用户端不显示：

- AI 初核待人工复核记录；
- 未审核候选；
- 内部流水线状态；
- 规则调试信息。

不要只在前端过滤：检查 API、服务层和数据装配路径，确保普通用户只能获得 published/已审核版本。管理后台仍可按权限查看待审核数据。

### 7.6 岗位列表卡片

默认只显示五项信息：

1. 地区 + 岗位名称；
2. 用工性质 + 学段 + 招聘人数；
3. 匹配状态；
4. 报名截止；
5. 一句关键依据或风险。

加一个主行动“查看判断依据”或按状态生成的明确动作。关注和展开为低强调操作。官方原文、岗位附件、完整条件、版本、纠错和详细来源下沉到详情页。

卡片规则：

- 最多一个主要状态标签；
- 最多一句摘要；
- 最多一个实心主按钮；
- 示例和真实数据必须明显区分；
- 卡片高度尽量稳定；
- 列表卡内部有多个动作时，整张卡不能同时作为一个冲突点击目标。

### 7.7 机会详情 `/opportunities/[unitId]`

按三层组织：

1. 结论 + 唯一下一步；
2. 已满足 / 还需补充 / 建议确认 / 不满足的摘要；
3. 官方原文、岗位表定位、核对时间、版本差异和纠错。

要求：

- “官方要求”“系统预筛”“你的回答/备注”视觉上明确区分；
- 专业或其他歧义提供可复制的官方咨询问题；
- 外部链接明确标记并安全打开；
- 外部官方网站打不开时，不影响已审核内容查看；
- 关注后即时反馈“已加入关注，时间已加入日程”，并提供撤销；
- 取消关注或更换主要目标前说明对日程和备考的影响；
- 不在首层显示技术性规则版本编号。

### 7.8 日程 `/schedule`

把页面从日期集合改为行动页：

- 第一屏只显示下一项需要处理的行动；
- 展示机会名称、截止/节点、材料进度和一个行动按钮；
- 第二层按“今天 / 7 天内 / 稍后 / 待官方通知”或等效结构呈现时间线；
- 默认不展示月历；
- 未确定时间保持“待官方通知”；
- 时间冲突提示双方机会，不替用户决定；
- 已完成事项收起，过期事项进入历史；
- 单个机会提醒可关闭并撤销；
- 没有关注时给出解释型空状态和“去看看机会”。

### 7.9 备考 `/study`

根据真实状态只渲染当前阶段：

- 无主要目标 → 去选择主要目标；
- 考试信息未确认 → 核对考试内容；
- 计划草稿 → 确认 7 天计划；
- 执行中 → 今天只做这一项；
- 今日完成 → 简短完成反馈和明日预告；
- 周期结束 → 周复盘。

本周其他安排、备选目标、资料诊断和历史版本进入第二层或第三层。保留现有计划和重排领域规则，不把未完成任务全部堆到次日，不自动为多个备选目标生成计划。

### 7.10 “我的” `/me`

作为个人信息和次级能力的聚合入口，顺序建议：

1. 主要目标和当前下一步；
2. 进入备考（仅有主要目标时出现）；
3. 我的报考信息；
4. 通知与提醒；
5. 我的资料；
6. 纠错记录；
7. 隐私、数据和账号。

不要把“我的”做成统计仪表盘。每一行说明去哪里或能做什么。

## 八、导航实施要求

### 移动端

- 保持并完善现有“机会 / 日程 / 我的”底部三 Tab；
- 高度、触控区域、安全区、激活状态和二级路由高亮正确；
- 问答、首页、说明、登录不显示底部导航；
- 备考不是一级 Tab，只从主要目标和“我的”进入。

### 桌面端

用户端采用简洁顶部导航：品牌在左，机会/日程/我的为主要入口，账号在右。移除当前宽侧栏中常驻的大型目标卡和 Emoji Logo。管理后台保持独立后台布局，不套用用户端顶部导航。

如果现有 AppShell 结构使一次切换顶部导航会高风险破坏大量行为，应先完成可独立验收的轻量版本：收窄侧栏并删除常驻目标卡，同时在最终报告中说明未切顶部导航的技术原因和后续任务。不能默默保留现状却声称已完成。

## 九、用户语言词表

用户可见页面按以下方向统一，技术字段名和数据库枚举不要求改名：

| 内部/旧表达 | 用户表达 |
|---|---|
| 基础画像 | 你的报考信息 |
| 匹配维度 | 报考条件 |
| 即时匹配已发布公告 | 根据最新公告重新核对 |
| UNKNOWN | 还不能判断 |
| MANUAL_REVIEW | 建议向招聘单位确认 |
| 闸门失败 | 这个机会暂时不能推荐 |
| 数据集 | 信息来源 |
| 规则版本 | 判断依据更新于 |
| 服务端正式结果 | 最新结果 |
| localStorage | 仅保存在这台设备 |
| 后端/API 加载失败 | 内容暂时没有加载出来 |
| role=primary | 主要备考目标 |

全仓搜索用户端可见文案；错误、空状态和帮助文本中不得出现 Mock、后端、API、数据库、localStorage 等实现术语。管理后台和开发日志可以保留准确技术用语。

## 十、通用页面状态

为核心用户页面建立一致但不僵化的状态组件和文案：

### 加载

- 使用接近真实内容形状的骨架；
- 保持布局稳定；
- 长时间加载说明正在获取什么；
- 不阻塞已经可用的页面区域。

### 空状态

- 说明为什么为空；
- 说明是否代表真的没有机会；
- 给出一个主要恢复行动；
- 不只显示“暂无数据”。

### 错误

- 说明发生了什么；
- 说明用户输入是否保存；
- 给出重试或返回路径；
- 将焦点和辅助技术提示放到正确位置；
- 不泄露内部异常详情。

### 成功与撤销

- 关注、保存、关闭提醒等可恢复操作使用非阻塞状态消息；
- 提供撤销；
- 状态消息使用可被屏幕阅读器识别的语义；
- 不因为轻量成功操作弹出模态框。

### 不可逆操作

- 使用确认界面；
- 明确列出影响的数据和功能；
- 危险操作与取消操作视觉层级清晰。

## 十一、动效

- 使用 150–250ms 的轻量淡入、位移、选中和进度变化；
- 动效解释状态变化，不制造等待；
- 只有完成完整问答等关键节点允许一次轻量庆祝；
- 不使用假 AI 输入、自动轮播、连续撒花、所有卡片悬浮或模块飞入；
- 支持 `prefers-reduced-motion`；
- 动画期间重要操作仍可用。

## 十二、响应式与无障碍

至少验证 320、375、768、1024、1440px：

- 320px 无横向滚动；
- 虚拟键盘不遮挡字段、错误和主操作；
- 底部导航不遮挡最后内容；
- 重要触控目标建议至少 44×44px；
- 页面可用键盘完整操作；
- 焦点顺序符合视觉与业务顺序；
- 焦点指示清晰；
- Dialog/Drawer 打开后管理焦点，关闭后返回触发控件；
- 所有输入有持久标签，placeholder 不代替 label；
- 错误以文字说明并关联到字段；
- 颜色不是唯一状态信号；
- 文字和控件对比度符合 WCAG AA；
- 200% 缩放仍能完成核心流程；
- 屏幕阅读器能够获知加载、成功、失败和进度变化；
- 外部链接、展开按钮和图标按钮具有清晰可访问名称。

## 十三、分析事件与隐私

保留现有事件名称和去重语义，只有缺口明确时才新增。至少能够观察：

- 首页直接开始；
- 打开 30 秒说明；
- 从说明开始；
- 恢复上次进度；
- 每组完成/跳过；
- 回答摘要修改；
- 初步结果曝光；
- 查看优先机会；
- 查看判断依据；
- 关注；
- 日程行动；
- 设置主要目标；
- 开始第一项备考任务。

事件不得包含专业原文、身份证、联系方式或其他不必要的个人信息。seed/demo 事件与 live 事件继续隔离。事件修改后同步事件字典、测试和端到端脚本。

## 十四、实施顺序

严格按以下阶段推进，每一阶段完成后运行相关测试再进入下一阶段：

### 阶段 A：基础与设计系统

- 语义色彩、排版、间距、圆角、阴影；
- 按钮、选择项、Disclosure、Drawer/Bottom sheet、Skeleton、Status message 等必要基础组件；
- 用户语言词表；
- 保留管理后台现有视觉，除非共享组件必须兼容。

完成标准：新组件有可访问状态和测试；未进行页面大规模复制粘贴。

### 阶段 B：首次体验

- 首页双入口；
- 30 秒说明；
- 问答减负；
- 阶段反馈；
- 继续上次进度；
- 结果页回答摘要。

完成标准：访客可以从首页独立完成问答、修改任一组并看到结果；刷新和返回不丢状态。

### 阶段 C：机会决策

- 机会页压缩；
- 五项岗位卡；
- 详情三层；
- 未审核数据退出用户端；
- 关注成功与撤销。

完成标准：普通用户只看到已发布信息；能在 10 秒内识别优先机会、截止时间和下一步。

### 阶段 D：行动与持续使用

- 日程行动页；
- 备考状态页；
- 我的聚合；
- 移动底部导航和桌面导航；
- 恢复上次行动。

完成标准：关注机会自然进入日程，主要目标自然进入备考，各状态只有一个主要行动。

### 阶段 E：状态、无障碍、指标和收口

- 空、错、加载、成功、撤销；
- 响应式、键盘、焦点、对比度、减少动态效果；
- 埋点和 QA 脚本；
- README 与实现状态同步。

完成标准：所有核心状态可复现、可恢复、可自动或人工验收；文档不夸大未验证效果。

## 十五、明确不在本轮实现

- 完整 AI 聊天机器人；
- 强制公众号长文章；
- 新的自由注册或短信/微信登录；
- 首页统计仪表盘；
- 地图找岗位；
- 排行榜、积分和强游戏化；
- 复杂月历；
- 多目标自动时间分配；
- 新的远程字体、CDN 或外部 UI 运行时依赖；
- 为“高级感”添加大量动画或装饰；
- 与页面体验无关的后端架构重构。

## 十七、代码质量要求

- 优先复用现有领域函数、服务和组件；
- 页面只负责展示和交互，资格计算保持在 domain/service 层；
- 不复制同一业务规则到多个页面；
- 使用语义化组件和 Token，避免散落新的硬编码颜色；
- 不引入只解决一个轻量 UI 问题的大型依赖；
- 保留现有路由兼容和存储键；
- 数据迁移不是本任务默认方案；确需迁移时先说明风险并提供可回退方式；
- 日志不输出密码、会话、个人画像原文或服务端密钥；
- 无关文件不格式化、不重写；
- 删除旧代码前证明没有路由、测试或运行时调用依赖。
