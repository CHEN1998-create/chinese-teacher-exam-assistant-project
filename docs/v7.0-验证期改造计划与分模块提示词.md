# v7.0 验证期改造计划与分模块提示词

更新时间：2026-10-05  
适用位置：根目录文档、frontend、backend。三个位置各有 Git 状态，修改前分别检查。  
使用方式：每轮复制“共用提示词”与一个模块提示词；验收通过后再执行下一模块。

## 一、目标澄清与信息梳理

原始需求：基于现有产品体检，制定按顺序执行的修改计划，提供可直接修改和复用的提示词，并为产品重新命名。

显性目标是将现有 v6.1 体验调整为 v7.0 验证版。真正要验证的是：有语文教师招聘意愿、但目标批次或自身资格尚不确定的用户，能否借助真实官方机会、逐项资格解释，完成后续报考动作。

已知条件：

- v7.0 PRD 已把完整备考降为 P1，当前代码仍把“备考”放在一级导航；README 仍以 v6.1 为唯一需求来源。
- 匹配、公告版本、关注、日程、受邀账号和备考功能已有代码，可以增量修改。
- 访客预览使用固定日期的演示机会。真实试用必须使用实时复核的官方机会。
- 分析事件主要保存在各用户浏览器，无法直接作为跨设备受邀试用的可信汇总。
- 现有关注和状态流转未形成完整的报名材料清单及官方咨询记录。
- 真实覆盖地区、首批用户招募渠道、岗位复核人、受邀访问地址仍需项目负责人确定。

实施约束：首轮只开放语文学科；用户看到的机会必须与官方公告和核对时间对应；公开演示和真实受邀试用的数据与指标分别管理；现有备考数据和旧入口需要兼容；受邀试用必须在目标用户的普通网络中可访问。需由产品负责人确认的人力、预算与首批地区，会影响模块 1、2、8 的范围。

### 数据摸底与待补基线

根目录研究报告中的 35 个表面独立用户样本和 24 个官方招聘批次提供问题线索，但没有测得真实使用率。当前没有可信的画像完成率、结果理解率、关注率、7 日报考推进率和单条公告维护成本。v7.0 PRD 的 70%、60%、40% 等数字应视为验证目标，不应写成已实现或稳定行业基准。

核心指标建议口径：分母为完成基础画像、获得至少一个真实有效机会且已满 7 日观察期的受邀用户；分子为其中在 7 日内关注机会，并完成至少一个报考推进动作的用户。窗口从首次获得有效机会开始。有效动作分别统计：补充资料并导致结论更新、完成报名材料、标记准备报名或已报名、设主要报考目标。学习计划行为单列为 P1 探索，不计入 P0。演示 seed、员工与测试账号不计入。

## 二、实施顺序

| 顺序 | 模块 | 输出物 | 验收方式 | 主要责任 | 依赖 |
|---|---|---|---|---|---|
| 0 | 产品基线 | v7.0 范围表、指标口径、试验方案 | 与 PRD 和当前实现逐项对照 | 产品负责人 | 无 |
| 1 | 真实机会台账 | 官方来源、证据、覆盖范围、更新流程 | 真实岗位抽查及变更演练 | 运营＋开发 | 0 |
| 2 | 10—15 人人工验证 | 访谈、逐人匹配、7 日行为记录 | 用户复述依据和真实动作 | 产品负责人＋运营 | 1 |
| 3 | 导航与信息架构 | 机会／日程／我的、备考次级入口 | 手机与桌面路径走查 | 设计＋前端 | 2 |
| 4 | 首页与画像 | 新价值表达、五组问答优化 | 5 人独立可用性测试 | 设计＋前端 | 3 |
| 5 | 结果与报考动作 | 精简列表、证据详情、材料清单、咨询模板 | 从真实机会走到一次推进 | 前后端＋设计 | 4 |
| 6 | 公告变化与提醒 | 版本差异、影响说明、日程更新 | 延期、取消、条件变化演练 | 后端＋运营 | 1、5 |
| 7 | 指标与试用看板 | 服务端事件、漏斗、去重和对账 | 手算样本与看板一致 | 前后端＋产品 | 5、6 |
| 8 | 20—50 人受邀试用 | 7 日报告、错误复盘、下一轮决策 | 真实用户和数据质量复盘 | 产品负责人 | 0—7 |

关键路径：统一口径 → 真实官方机会 → 10—15 人人工观察 → 根据结果改造核心流程 → 20—50 人受邀试用。模块 3—7 可以提前准备设计或技术方案，实际范围应依据模块 2 的发现收敛。

建议节奏：模块 0—1 约 3—5 个工作日，模块 2 至少覆盖 7 日观察，模块 3—7 视首轮发现约 2—4 周，模块 8 至少再覆盖一个完整 7 日窗口。这只是单个小团队的排期假设；招聘渠道、公告复核人和受邀环境未确定时，不把它写成对外日期承诺。

进入产品改造前，至少有 5 位用户能理解匹配状态和下一步，且出现真实关注或推进。进入受邀试用前，真实机会证据和变更流程可运行，服务端指标可核对，真实访问地址可用，没有已知高影响资格错误。10—15 人样本只适合发现问题和判断方向，不适合推断稳定转化率。

主要风险：岗位不足、资格误判、公告更新不及时、演示数据混入指标、本地事件丢失、旧路由或数据被误删、受邀环境无法访问。对应处理是缩小首批地区、复核高影响字段、记录更新时间、区分 seed/live、服务端采集、兼容旧入口和发布前真实网络验收。

## 三、共用提示词

每轮新对话先复制这一段，再复制一个模块提示词。将【方括号】替换为实际选择；尚未确定的地方保留“待定”。

~~~text
你正在维护 E:\游戏\考编助手 项目。先阅读根目录的 PRD-全国教师公开招聘助手-v7.0-研究验证版.md、docs/v7.0-验证期改造计划与分模块提示词.md、frontend/AGENTS.md、本轮涉及的代码与测试。v7.0 是本轮验证目标，v6.1 文档描述现有实现；请先列出两者差异，再修改。

项目有根目录文档、frontend、backend 三个独立 Git 工作区。分别检查改动状态，保留用户已有和无关修改。只完成本轮模块，复用已有匹配、公告版本、关注、日程、登录和权限能力。备考能力先保留，不自行删除用户数据或修改真实部署。

产品面向【首批地区：待定】的语文教师招聘目标用户。主要推荐必须有可追溯官方来源、未过期且无已知明确不符合项。逐项区分官方事实、系统判断、用户自行确认和未知；缺信息不能判不符合；未覆盖地区写“暂未收录”。显示核对时间、证据和版本变化。演示数据明显标记，不能进入真实指标。

修改前报告现状证据、拟改文件、数据兼容风险和本模块验收方式。修改后报告改动、验证结果、仍需人工处理的事项。只为高风险规则和关键路径写必要测试。不要把未经实际用户验证的目标数字写成已达成。
~~~

## 四、按顺序执行的模块提示词

### 模块 0：统一基线

~~~text
只修改产品和实施文档。对照 v7.0 PRD、v6.1 PRD、frontend/README.md、backend/README.md 与当前页面，列出“保留／本轮新增／降级 P1／尚未实现”的范围表。明确目标用户、首批地区、真实机会标准、四档匹配、有效推进动作、10—15 人试验方法、停止条件与负责人。让文档读者清楚 v7.0 是本轮目标、v6.1 是现有实现，不把待验证能力写成已上线。交付版本决策记录和模块 1—8 的验收清单。验收：每项 P0 有 PRD 依据；指标的分子、分母、时间窗、排除项完整。
~~~

### 模块 1：真实机会与覆盖台账

~~~text
围绕【首批地区】建立可人工维护的真实语文教师招聘机会台账。先审计 backend 的来源、快照、审核与发布流程，补齐首轮必需的官方链接与附件、报考单元、用工性质、资格证据、核对时间、补充公告关系和责任人。高影响字段无法核验就降级，不进入最高优先推荐。前台公开实际覆盖地区、批次和核对时间；未覆盖写“暂未收录”。记录每条机会采集、复核和更新的人时。交付台账模板和更新流程。验收：抽 3 条真实机会能从列表追到官方原文；演练延期、取消、来源失效，旧版本保留且推荐状态正确。
~~~

### 模块 2：10—15 人人工服务验证

~~~text
准备一轮 10—15 名目标用户的人工岗位匹配试验。交付招募筛选题、知情说明、访谈脚本、逐人记录表、7 日跟进表和复盘模板。每人收集最少画像，人工提供 3—8 个有官方来源的真实候选，展示四档状态、依据、缺失项及下一步。让用户在无提示下复述一条依据和一条不确定项；记录关注、补信息、咨询官方、准备材料、报名与未行动原因，并记录岗位采集和复核人时。在其中 5—8 位用户中加做名称测试：不先解释产品，让用户说出候选名让他们想到什么、最可能提供什么服务、最容易记住哪个，再展示产品描述看理解是否变化。没有实际用户或数据访问时，只生成研究工具与待填项目，不编造结果。交付“继续改造／先修规则与数据／缩小用户范围”的判断。
~~~

### 模块 3：信息架构和导航

~~~text
依据模块 2 发现，把一级导航调整为“机会／日程／我的”。日程首屏承接下一项报考动作、材料与时间节点；我的集中画像、地区和用工偏好、通知、隐私、纠错记录。将备考移至已设主要报考目标后的次级或受控入口，保留 /study 数据和旧路由兼容。用户可见文案统一为“主要报考目标”；技术字段先评估兼容性再改。交付页面地图、移动端/桌面端导航与路由迁移表。验收：访客、普通用户、工作人员路径正常；原关注、主要目标、日程与备考数据不丢。
~~~

### 模块 4：首页与画像

~~~text
优化价值首页和 /onboarding，让首次访问者理解“官方语文招聘机会＋可解释资格预筛＋下一步”。首页首屏显示当前真实覆盖范围、核对时间与明确标示的结果示例；主按钮进入无需登录的资格预筛。保留五组渐进问答，优化地区直接选择、进度名称、资料用途、草稿恢复、返回修改和移动端下一步。允许合适的“不确定／暂不提供”路径；若最低必要条件缺失，解释为何暂不能给结果。未经测量不要写“2 分钟完成”。验收：5 名未参与设计者独立操作，记录 10 秒理解、步骤流失、完成时长、手机可用性；没实测就标待测。
~~~

### 模块 5：结果、详情与报考行动

~~~text
改造 /preview、/opportunities、/opportunities/[unitId] 及必要后端数据。列表卡第一层只展示报考单元、用工性质与学段、人数、截止时间、四档状态、关键依据或风险、一个下一步；默认折叠长证据。详情首屏按“结论 → 现在做什么 → 最关键依据与不确定项 → 截止与材料进度”组织。关注后生成公告要求的报名材料清单，逐项标适用人群、状态和来源。提供官方咨询方式、可复制问题模板和用户自行确认记录，不把用户记录写成官方事实。每个状态只突出一个主按钮。验收：从一个真实机会完成关注、补信息或人工确认、材料准备、进入官方报名入口；四档、空结果、过期和失败状态可理解。
~~~

### 模块 6：公告变化、日程与可信状态

~~~text
复用公告版本与日程能力，让补充公告、延期、岗位取消和资格变化形成“旧值 → 新值 → 对我的影响 → 下一步”。变化关联原招聘事件，旧版本不可覆盖；更新已关注机会的资格结论、截止状态和待办，并给受影响用户站内说明。来源失效、字段冲突、审核未完成分别展示可信状态；不确定时降级。时间未定写“待官方通知”。验收：延期、取消、条件变化、来源失效四种情境端到端演练；提醒不重复，未受影响用户不被误通知。
~~~

### 模块 7：真实指标与试用看板

~~~text
审计 frontend/src/lib/analytics 和 backend 的持久化能力，建立受邀试用所需的服务端事件与去重。按本文件定义的 v7.0 7 日有效目标推进率计算，单列补信息后结论变化、完成材料、准备报名、已报名与设主要报考目标人数。学习计划行为只作 P1 探索。区分 seed/live、测试/真实用户、演示/真实机会；跨设备与访客登录迁移不重复计数。增加画像各步、咨询模板复制、官方联系入口、材料完成、报名入口打开、结果变化等必要事件。事件不记录资格原文和证件信息。交付指标字典、事件表、看板和与人工台账对账方法。验收：手算少量样本并与看板比较，覆盖未满 7 日、重复点击、跨设备、取消关注和空样本。
~~~

### 模块 8：受邀试用与决策

~~~text
模块 0—7 验收后，准备 20—50 人、至少一个完整 7 日窗口的受邀试用。先核实真实受邀地址、账号和数据隔离、目标用户普通网络访问、岗位复核责任与纠错处理人；缺一项就标待办，不写“已上线”。交付发布前检查表、用户指引、每日数据与错误复盘表。试用后报告画像完成率、有效机会率、依据理解率、关注率、7 日推进率、各推进动作人数、公告维护人时和高影响错误，并说明样本量及流失原因。基于真实行为给出继续聚焦资格判断、收窄覆盖、扩学科或验证备考 P1 的建议。
~~~

## 五、名称方案

推荐试用名：**教招有据**。它把“教师招聘”与“判断有官方依据”放进四个字里，语气稳妥，也不会暗示百分之百可报。建议完整展示为“教招有据｜教师招聘机会与资格预筛”。

| 名称 | 品牌契合与记忆点 | 主要取舍 |
|---|---|---|
| 教招有据 | 直接指向教师招聘、官方依据和逐项解释；四字短、好读 | 需要副标题说明也能发现机会、跟进报名 |
| 教招明白 | 强调把复杂条件讲清楚；口语自然 | “明白”偏通用，辨识度可能较低 |
| 教招路标 | 强调报考下一步；视觉符号容易设计 | 资格判断的“有依据”表达较弱 |
| 教招有谱 | 轻松好记，有“心里有数”的感觉 | 语气稍轻，需测试是否削弱信任感 |
| 教招寻岗 | 直接强调找岗位，容易理解入口 | 容易被当成普通公告聚合工具 |

公开搜索未发现这些完整名称的明显同名产品；这只是初步网络排查，不等于商标或域名可注册。正式更名前，使用中国商标网核查相同及近似商标，并查询域名、应用商店、小程序和公众号占用。先对 5—8 名目标用户测试名称理解与记忆，再替换首页、导航、页面标题、README 和对外介绍。Git 仓库名和技术包名可以最后再改。
